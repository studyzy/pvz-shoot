## 0. 一页纸结论

| 问题 | 现状 | 结论 |
| --- | --- | --- |
| 手机 / iPad 开房，第二个人很卡 | **僵尸由房主模拟**（`DuoSession.sendHostState` 20Hz 发全量快照，`ZombieManager` 只在 host 跑 AI）。手机房主同屏 14 只僵尸的 AI + 骨骼 + 快照序列化，每帧本身就掉到 20~30 fps；掉帧越狠，快照越稀，客人看到的僵尸越顿挫 | **根因不是网络带宽，是房主客户端的帧率被直接映射成客人的游戏体验**。不把房主从模拟链路里摘掉，任何带宽优化都救不回来 |
| 你的约束：服务器性能够呛、不能跑浏览器 | — | **绝不用无头 Chrome / Electron 当服务器**。用现有 Node 进程跑 **不依赖 Three.js 渲染** 的纯逻辑模拟；每场 2 人、同屏 ≤14 只僵尸，实测单场 **0.096 ms/tick**（见 §1.2） |
| 单人必须完全离线可玩 | 已经是纯静态站（`Game` 本地模拟） | 保留。**同一份模拟代码**同时被浏览器（单人）和 Node（联网）调用，单人路径不新增任何网络依赖 |
| 不要依赖房主客户端性能 | — | 删掉房主权威。两台客户端都只是「渲染 + 本地输入预测」，服务器 = 唯一模拟器 |

**一句话方案**：把现在 `Game` 里的**模拟**和**渲染**拆开，模拟层变成能在 Node 里跑的纯逻辑（`MatchSim`），服务器每场启动一个 `MatchSim`，20–30 Hz 广播二进制快照；客户端只做**插值渲染 + 输入预测**。房间「房主」这个身份从协议里彻底消失。

**在 2C8G Lighthouse 上的可行性（本次核算，详见 §1.2）**：

| 维度 | 结论 |
| --- | --- |
| CPU | **余量 10~40 倍**。最保守口径下单核可跑 43 场，当前 `MAX_MATCHES=8` 只用约 1% 单核 → **worker 分片砍掉** |
| 内存 | 每场 ~1 MB，**余量数千倍** |
| 游戏内出网带宽 | 0.14 Mbps/场，8 场 1.15 Mbps，**远低于套餐带宽**（Lighthouse 带宽官方不承诺，但余量足够） |
| 月流量包 | 游戏内快照 < 10 GB/月；**真正的流量大头是 27 MB 静态资源**，→ 必须做 `immutable` 缓存（§5.1） |
| 语言选型 | **沿用现有 JavaScript 部署，不做 Rust 重写**：换语言只能优化 30.8 µs/tick 的逻辑开销，8 场从 0.50 ms 降到 0.22 ms，都在 33.3 ms 预算的噪声里；代价是在 Rust 和 JS 之间维护两份模拟逻辑（详见 §6.5） |
| 结论 | **方案在这台机器上完全成立，且留有巨大余量。** |

## 1. 病根分析（先定性，再动手）

### 1.1 现在的数据流

```
  手机房主 rAF(掉帧到 20~30fps)
      │  Game.update()   ← 玩家、14 只僵尸 AI、骨骼、粒子、武器、阳光球 全都在这
      │  sendHostState() 每 50 ms（约每 1~2 个 rAF 一包），JSON
      ▼
  VPS：wss relay（只看字符串，不解析内容）  ← 服务器越多，转发吞吐越高，但 CPU 只是 memcpy
      ▼
  客人：Zombie.applyNetState() 直接 set 位置（无插值），0.2 m 软校正
```

**三条互相独立的卡顿来源**，都在房主侧：

| # | 来源 | 证据 |
| --- | --- | --- |
| A | **房主掉帧 → 快照变稀**。`sendHostState` 挂在 `Game.loop` 的 rAF 上（`Game.js:1572` → `DuoSession.update` 用 `dt` 累积），不是 `setInterval`。手机房主 25 fps 时快照实际是 25/2 ≈ 12.5 Hz 且**抖动** | `DuoSession.js:286-299`、`Game.js:1622-1643` |
| B | **快照是稀疏采样的绝对状态**，`applyNetState` 直接写 `root.position`（`Zombie.js:1526-1560`），客户端没有插值/外推。20 Hz 抖动 + 无插值 = 每 50~80 ms 一次跳变，肉眼就是「幻灯片」 | `Zombie.js:1526`、`ZombieManager.js:413-431` |
| C | **房主算力被两头吃**：一边渲染（14 只 × 1 万面），一边跑全部 AI + 给客人算全身快照（`JSON.stringify` 每包 ~2.7 KB 瞬时拼接）。手机本来就贴着 43 fps 的自动降分辨率底线（`Game.js:1653`），再加一整套模拟是雪上加霜 | `ZombieManager.js:89`、`DuoSession.js:355` |

> **注意**：带宽不是主因。14 只僵尸 × 196 B ≈ 2.7 KB/包 @20 Hz ≈ 54 KB/s，家宽和 4G 都无所谓。所以「压缩、降频、差量」这类优化**解决不了**这个症状——一降频，B 只会更严重。

### 1.2 服务器吃得下吗（在 2C8G 腾讯云 Lighthouse 上实测核算）

**目标机器已确定：2 核 / 8 GB 腾讯云轻量应用服务器（Lighthouse）。** 下面全部按这台机器核算。

实测环境：本机 `vitest` 的 jsdom 环境（比裸 Node 慢，结果偏保守），用**真实 `Zombie` 类 + 真实 glb 骨架 + 真实 AI**，不是估算：

| 场景 | 14 只僵尸每 tick 的 `update()` | 说明 |
| --- | --- | --- |
| 14 只普通僵尸在走 | **0.011 ms** | 已验证：僵尸真的从 z=-12 走到 z=18.3，`animSpeed=2.05`，不是空转 |
| 重阵容（ boss + 骷髅 + 橄榄球 + 气球 + 锥桶 ） | **0.040 ms** | 全部 `alive` |
| **技能流打满 + 每 tick `serialize()`** | **0.096 ms** | 蘑菇王/巨人/龙/发条兵/报时兔/杰克盒/博士同屏互殴，14 只全程存活 |

**外推到 Lighthouse 共享 vCPU**（腾讯云轻量不保证 CPU 型号，按最悲观口径）：

| 单核折算 | 单场每 tick | 30 Hz（预算 33.3 ms）下单核可容纳 |
| --- | --- | --- |
| 本地核 50% | 0.19 ms | **173 场** |
| 本地核 25%（很保守） | 0.38 ms | **86 场** |
| 本地核 12.5%（极端） | 0.77 ms | **43 场** |

**结论：CPU 完全不构成瓶颈，余量有 10~40 倍。** 项目当前的 `MAX_MATCHES=8` 在这台机器上连 1% 的单核都用不到。内存更不用说——模拟层不碰 `Scene`/`Material`/几何体，每场只需 ~1 MB，8 GB 够几千场。

> 所以原计划里的「worker_threads 分片扩容」在 2C8G 上是**多余的**，M4 该项直接砍掉（YAGNI）。单进程单核足矣。

### 1.2.1 真正的瓶颈：出网带宽与月流量包

Lighthouse 的计费方式决定了这才是要盯的指标（官方定义，见 `cloud.tencent.com/document/product/1207/44368`、`/44755`）：

- 套餐里的「带宽」是**出网（下行）带宽上限**；**流量包只统计出流量**，每月按自然月重置，超出部分按量计费。
- 官方明确写明：**套餐带宽「不作为业务承诺指标」**，高峰期资源争抢时可能被限制。

按二进制快照（300 B/帧 @30 Hz，14 僵尸 + 2 玩家 + 阳光球）核算：

| 项 | 数值 |
| --- | --- |
| 每客户端下行 | 8.8 KB/s = **0.07 Mbps** |
| 每场（2 人） | 17.6 KB/s = **0.14 Mbps** |
| 8 场并发 | 1.15 Mbps |
| 1 场跑 1 小时 | **60 MB** |
| 1 场 24 小时 | 1.45 GB |

**换算到 2C8G 套餐（通常 4~6 Mbps 出网 + 每月数百 GB~1 TB 流量包）**：游戏内网速只占 4~6 Mbps 里的一小截，8 场并发 1.15 Mbps 也远没打满；流量方面，假设每月总共玩 60 小时、平均 2 场在跑，约 **7 GB/月**，对流量包是零头。

**⚠️ 但真正的流量大头不是游戏，是静态资源**：`public/` 现在有 **27 MB**（一堆 glb 模型，最大 1.4 MB/个）。每个新玩家首次打开页面就要下载这 27 MB：

| 场景 | 月出流量 |
| --- | --- |
| 20 个不同用户 × 2 次冷启动 | ~1 GB |
| 50 个不同用户 × 3 次冷启动 | ~4 GB |
| 100 个不同用户 × 3 次冷启动 | ~8 GB |

结论：
1. **游戏内快照流对 Lighthouse 完全无压力**，放心用 WebSocket。
2. **静态资源要单独做缓存策略**（下面 §5.1 新增的 M0 子项）：`dist/assets/*` 带 hash 可设 `Cache-Control: immutable`，`models/*.glb` 是构建期拷贝的固定文件、同样可长期缓存——做好之后**同一用户重复进入几乎不占流量**。
3. 若将来用户量上去，优先考虑把静态资源放 CDN 或对象存储，而不是升级 LuaHouse 套餐——这是标准做法，也省得多。

### 1.3 为什么「不跑 Chrome」是对的、而且不需要跑

无头 Chrome 的方案不可行的三点（都会踩）：
- 每个浏览器实例 300~500 MB 起，2 核 2 GB 的小 VPS 一个都开不下；
- WebGL 渲染层在服务器上是纯浪费（僵尸的 1 万面、阴影、后处理都要执行，只为输出一个位置）；
- `rAF` 在无头/后台标签页会被节流到 1 Hz —— 模拟直接停摆，这是**致命**的。

正确做法：**模拟代码本身不依赖渲染**。现在它其实「只差最后一步」——僵尸的 ctx 依赖只有 6 个字段，其中 5 个是可选副作用（见 §3.2 的移植清单），`Player` 完全不碰渲染（`applyCamera` 是独立的输出方法）。所以这次是「把模拟从渲染里剥出来」，不是「重写一个服务器」。

## 2. 目标架构

### 2.1 三层 + 一个共享核心

```
        ┌────────────────────────── 共享核心 packages/sim（纯 ES Module，零渲染依赖）─┐
        │  MatchSim  = 固定步长 30 Hz 的权威世界                                      │
        │    PlayerSim × 2 · ZombieSim × ≤14 · ProjectileSim · SunOrbsSim · PickupSim  │
        │    WaveDirector · SunEconomy · SeededRandom(simSeed)                        │
        │  输出：输入 → 世界事件（event log）+ 状态快照（snapshot）                     │
        └───────────────┬───────────────────────────────┬──────────────────────────────┘
                        │ 同一份代码                      │ 同一份代码
          ┌─────────────▼────────────┐        ┌─────────▼─────────────────────────┐
          │ 浏览器 · 单人             │        │ Node Worker · 每场一个 MatchSim    │
          │  MatchSim 跑在本地         │        │  （M2：先跑在主进程）              │
          │  渲染层订阅事件+快照        │        │  广播快照 (UDP/WS)                │
          └──────────────────────────┘        └─────────┬─────────────────────────┘
                                                        │ 快照 20~30 Hz
     ┌───────────────────────────┬──────────────────────┴───────────────────────┐
     │ 客户端 A（手机 / iPad / 桌面）│ 客户端 B                                 │
     │ ClientNet：输入预测 + 快照插值 + 本地特效                                    │
     └───────────────────────────┴──────────────────────────────────────────────┘
```

**关键判定**：单人模式 = `MatchSim` 直接跑在浏览器里，没有服务器、没有 socket。所以「单人不需要网络」不是额外要做的事，而是这个架构的**自然结果**——同一个 `MatchSim`，本地跑还是远端跑，只换一个「时钟源 + 输入源」。

### 2.2 权威归属（定死，别再改）

| 内容 | 权威 | 说明 |
| --- | --- | --- |
| 僵尸位置 / 血量 / AI / 技能 | **服务器 `MatchSim`** | 客户端一份都不跑 AI（`Zombie.remote` 分支保留，只做姿态插值） |
| 玩家移动 | **客户端预测 + 服务器裁决** | 客户端本地积分，服务器按同一份 `PlayerSim` 重跑，超出阈值 Snapped |
| 命中判定 | **服务器** | 客户端只发「我开了枪，方向是 D」，服务器做扫掠 |
| 阳光 / 补给 / 掉枪 / 计分 / 波次 | **服务器** | 现在 guest 的 `claim` / `sun` / `drop` 请求保留，改为服务器权威 |
| 粒子 / 音效 / 镜头震动 / 后坐 | **纯本地** | 永不进网络（现在也没进，保持） |

### 2.3 传输层

| 阶段 | 传输 | 理由 |
| --- | --- | --- |
| M2 / M3 | **WebSocket 二进制帧**（现有 `ws`，快照从 JSON 换 `DataView` 编码） | 零新依赖、零新运维；54 KB/s 的量级 WS 完全够 |
| ~~M5~~ | ~~WebRTC DataChannel 不可靠模式~~ | **已定案不做**（附录 A 决策 3）：WebSocket 的 0.14 Mbps/场 余量足够，WebRTC 只增加 TURN/打洞运维成本 |

> 服务器**必须**是自建 Node 进程（现在是 `npm run duo`），**不能**部署到 GitHub Pages——Pages 只跑单人。这一点 `AGENTS.md` 已经写明，本次不变。

### 3.2 模拟层移植清单（每一项都对应现有文件的具体位置）

**`Player` → `PlayerSim`**（`src/entities/Player.js`，335 行）
- `update()` 里的移动/碰撞/跳跃/回血/倒地计时**原样搬**，只删掉 `applyCamera()`（留在视图侧）。
- 已经是纯逻辑，没有 `import three` 以外的渲染调用；`THREE.Vector3` 可以继续用（`three` 的数学类在 Node 里能跑，实测通过），**不引入新依赖**。

**`Zombie` → `ZombieSim`**（`src/entities/Zombie.js`，1925 行，**最大的一块**）
- 要搬：`constructor` 的数值字段、`update()` 的 AI/寻路/攻击/技能状态机（约 1700 行）、`hit()` 的伤害/护甲/燃烧结算、`serialize`/`applyNetState` 的状态口径。
- 要留在视图侧：`buildRig`、`buildAnimations`、`play`、`applyFlash`、`applyTint`、`buildHat`、`mixer`、`shadow`、`model` 缩放、粒子/FX 调用。
- **ctx 依赖盘点**（这是能不能在 Node 里跑的唯一阻塞点，全项目只有这些）：
  | ctx 字段 | 用在哪 | 处理 |
  | --- | --- | --- |
  | `ctx.particles` | 死亡/爆头/燃烧的粒子 | 服务器传 `null`（模拟不产生视觉）；视图侧订阅事件播放 |
  | `ctx.sfx` | `startDeath`/`breakArmor` 等音效 | 同上，传 `null` |
  | `ctx.env` | 材质环境贴图 | 只被渲染用到，正本清源后模拟层不要它 |
  | `ctx.map` | `flowAt` / 边界 / 碰撞体 | **保留**：地图数据层（`FlowField`、`colliders`、`platforms`、`bounds`）必须能在 Node 算出，地图不放 Three 场景对象 |
  | `ctx.cloud` | 云园地图的铜钟/茶滴 | **保留**：`CloudCombat` 拆出 `logic` 部分；`serialize` 已有，天然适合做纯模型 |
  | `ctx.onAttack` / `ctx.zombies` / `ctx.player` | 回调与反向引用 | 改用 `MatchSim` 注入 |
- **视图侧改造**：`Zombie` 变成 `ZombieView`，消费 `ZombieSim` 的快照（复用现有 `applyNetState`/`remote` 分支，**几乎不用重写**——那条路已经为 guest 写通了，本计划只是让**服务器**也走这条路）。

**`ZombieManager` → `WaveDirector`**（`src/entities/ZombieManager.js`，18.6K）
- 要搬：`startWave` / `spawnOne` / `handleKill` / `damageArea` / `wavePlan` 配额（`SKELETON_MAX_ALIVE`、`AIR_QUOTA`）。
- 注意 `ctx.hud.showBanner`（悬赏播报）在 `ZombieManager.js:365`——改为**发事件** `{type:'bounty'}`，客户端收事件弹横幅。
- 注意 `ctx.sunOrbs.spawn`（掉落）——改为 `SunSim.spawn` 的纯逻辑调用。
- `pendingSplits`（粉史莱姆分裂）里尸体回收后生成子体的逻辑要保留原语义。

**`WeaponSystem` / `ProjectileSystem` → `WeaponSim` / `ProjectileSim`**
- 只搬「冷却、弹药、阳光扣费、`tryFire` 的弹道解算、`segmentSphereT` 扫掠、`aerial` 白名单」。
- 视图模型（GLB、后坐、摇摆）留在 `WeaponSystem`。视图只消费「开火了 / 命中谁 / 爆头」事件。
- **风险点**：`WeaponSystem.tryFire` 与相机强耦合（`WebGLRenderer` 无关，但依赖 `camera.position/quaternion`）。抽的时候把「从 (origin, dir) 开一枪」当成 `WeaponSim.fire(origin, dir)` 的接口，相机解算留在客户端；服务器用客户端上报的 `yaw/pitch` 重建 origin+dir，并做**视线校验**（现在 `applyGuestHit` 里的扫墙逻辑 `Game.js:855` / `:972` 直接搬过来）。

**`SunOrbs` / `SkySun` / `WeaponPickups` → `SunSim` / `PickupSim`**
- `SunOrbs` 现在的 `update` 已经把物理和 `group.position` 混在一起，拆开即可。`serialize`/`applyNet`/`updateRemote` 已有，改成纯逻辑后语义不变。
- `WeaponPickups.setShared/applyNetList/netList/onClaim/onDrop`（`WeaponPickups.js:256-392`）已经是「host 权威 + guest claim」的形状，**直接把 host 换成服务器**即可，改动量小。

**可播种随机（`SeededRandom`）**
- 现在模拟里只有 **1 处** `Math.random()`（`ZombieManager.js:165` 悬赏怪选取），其余随机在 `utils.js` 的 `rand()`。但 `rand()` 被模拟与渲染**大量共用**（掉落位置、粒子方向、地图生成）。
- 结论：**只把模拟需要的随机改成注入**（`sim.rng`），渲染的 `rand()` 保持不动。**不需要**整体确定性重放——本方案**不做 lockstep**，快照驱动，所以 P2P 式确定性不是硬需求。这一点很重要：不确定性会把工作量放大 5 倍。

### 3.3 网络协议 v2（定稿草案，实施前需再评审一次）

顶层消息保留 `hello/welcome/queue/peer/start/map/error/end/bye/rematch/ping/pong`，**删掉 `relay`**（字符串中继）。新增二进制帧（`Uint8Array`，第一字节 = 类型）：

| 帧 | 方向 | 频率 | 内容 |
| --- | --- | --- | --- |
| `INPUT` (0x10) | C→S | 30~60 Hz | `tickSeq`、`moveX/moveZ`（int8）、`yaw/pitch`（int16，1/1000 rad）、`buttons`（bitfield：jump/fire/shield/reload/丢枪/切枪/下一波）、`weaponIndex` |
| `SNAP` (0x20) | S→C | 20~30 Hz | 头部 `tick`、`ackInputSeq`（玩家各自的最后处理输入） |
|  |  |  | 僵尸段：`id(u16) type(u8) x/y/z(int16,cm) yaw(int8) hp(u16) state(u8) flags(u8)` |
|  |  |  | 玩家段：`pos, vel, hp, shieldHp, downedTimer, weaponIndex` |
|  |  |  | 阳光球段、补给段（id + 状态位）、经济（sun、scores、kills、wave、bossHp） |
| `EVENT` (0x30) | S→C | 事件驱动 | 刷怪 / 死亡 / 爆头 / 护甲碎 / 掉落 / 拾取 / 波次开始结束 / 悬赏 / 铜钟 / 空投 / 结算。**只做表现**，不改状态（状态永远以 `SNAP` 为准） |
| `CMD` (0x40) | C→S | 事件驱动 | 丢枪、切枪、claim 补给、申请下一波、举报等低频操作 |
| `SNAP_FULL` (0x21) | S→C | 重连/进局时一次 | 完整世界（替代现在的 `resync`），保证刷新后不丢装备 |

编码细节：
- **整数定点**：坐标 `int16` 厘米（±327 m，地图 90×90 够用），角度 `int8`（1/64 圈）或 `int16`，血量 `u16`。
- 预计单帧（14 僵尸 + 2 玩家 + 6 阳光球）**≈ 200~300 B**，@30 Hz ≈ 7~9 KB/s。对比现在 JSON 的 54 KB/s，**顺带省 85% 带宽**（但记住 §1.1：这不是主因）。
- 服务器维护**每场 1 秒的环形历史快照**（约 30 帧 × 300 B ≈ 9 KB），供命中回退用（现在 `DuoSession.history` 已经在客户端干了这事，搬到服务器后逻辑更干净）。

### 3.4 客户端网络栈（`ClientNet`）——这是「手感」的所在

沿用经典 Source/Halo 式三段结构，**单人模式下全部旁路**：

1. **输入预测（prediction）**：本地 `PlayerSim` 立刻应用输入并播放镜头；输入按 `(seq, 输入, dt)` 入本地队列。
2. **服务器和解（reconciliation）**：收到 `SNAP` 带 `ackInputSeq` + 服务器认定的玩家位置后，若与本地位置偏差 > `0.12 m`（现在是 0.2 m，`AGENTS.md` §5.12 写死），回滚到服务器位置，**重放未确认的输入**。注意：现有实现是「软校正 0.2 m」，那是本方案的降级版，正式版要做回放。
3. **实体插值（interpolation）**：僵尸/队友按 `renderTime = serverTime - INTERP_DELAY` 在最近 2 个快照之间线性插值；`INTERP_DELAY = 100 ms`（20 Hz 时 2 帧）+ 自适应（抖动大时自动加到 150 ms）。**这是解决「跳变」最关键的一步**，现在完全没有。
4. **外推上限**：超过 300 ms 没有新快照 → 该实体冻结（不要外推，僵尸速度方向随机外推会很怪），并亮「网络差」角标。
5. **本地即时反馈**：开枪立刻播动画/音效/后坐；命中表现**由服务器的 `EVENT` 驱动**——为避免「打完 80ms 才听到命中音」，客户端可以**本地预测命中闪光**（打空再纠正，概率极低），但伤害数字/血量/击杀以服务器为准。

### 3.5 服务器房间（`server/room.js`）

```
Room {
  matchSim     // src/sim/MatchSim.js 的实例
  players[2]   // { conn, lastInputSeq, inputBuffer, lastSeenAt }
  loop         // 固定 30 Hz 的 tick 驱动（每种 Room 一个 setInterval? 不：全局一个 30Hz ticker 遍历所有 Room）
  history      // 环形快照（命中回退）
}
```

- **不要**给每个 Room 开一个 `setInterval` —— 8 场 8 个定时器，事件循环抖动会让 tick 不均。用一个全局 ticker（`setTimeout` 自校正），一次遍历全部房间。
- **Room 里不能有任何 DOM / Three Scene / 材质**。这是硬约束，写进 ESLint 规则或在 CI 加一条「`src/sim/` 与 `server/` 中不得出现 `document.`/`window.`/`WebGLRenderer`」的 grep 测试。
- **断线重连**：保留现在的 45 s 座位保留 + `joinToken`；重连后发 `SNAP_FULL`。房主掉线不再结束对局（**这是本方案顺带修掉的 bug**：现在 `hello.page` 变了就 `HOST_RESET`，见 `DuoSession.js:19`；服务器权威后，谁掉线都只是「该座位 AI 托管 45 s」）。
- **房间没人则销毁**：两人都掉线 → 保留 45 s → 销毁 Room，释放 `MatchSim`。

## 4. 分阶段实施计划

原则：**每一步都能单独上线、都能 `npm test` 全绿**，不做「大爆炸式重写」。单人模式在每一步结束时都必须可用。

### M0 · 埋点与现状固化（0.5 天，先行）
- 在 `Game` 加可开关的性能探针：`window.__net = { fps, sendHz, snapGapMs, zombieCount }`。
- 在 `DuoSession.sendHostState` 记录**实际发送间隔分布**（p50/p95），在客户端记录 `applyNetState` 的**位置跳变量分布**。
- **基线采集方式（已定）：Chrome DevTools CPU 6x 降速模拟手机**，不用真机。

  > ⚠️ **这个替代方案有已知失真，必须写进结论**：CPU 降速能很好地复现「房主帧率掉 → 快照稀疏」这条主线（也正是本次的根因），但**无法复现**真机上的其他因素——iOS Safari 的 WebGL 驱动开销、内存压力与后台节流、真实 Wi-Fi/4G 抖动、iPad 的高分辨率填充率瓶颈。所以基线只能证明「刷新率下降会外包成客人的卡顿」这个因果，**不能当作真机性能的等价替代**。

- **因此追加一条硬性验收（M2 之后、上线之前，不可跳过）**：用一台真机做**改造前后各一次**的对比——改造前若没有真机基线，就只做「改造后真机可玩」的验收，并在文档里明确记为**未做前后对照**。这一条要如实记录，不要用桌面模拟数据冒充真机结论。
- **验收**：产出基线数据贴进本文件附录 C；至少能证明「房主 fps 与客人感知的僵尸移动平滑度强相关」。
- 不做这步就开始重构 = 赌。

### M0 补充：不要用模拟数据下结论
桌面 CPU 降速可以作为**开发期的回归护栏**（改完没人感觉变差），但不能作为**「问题已解决」的证据**。判断标准始终是：真机上第二个人是否还卡。

### M1 · 抽出模拟层（3~5 天，最大的一块，纯重构无行为变化）
1. 新建 `src/sim/`，按 §3.2 逐类搬迁；每个类**先从 `Player` 这种最简单的开始**（0.5 天，验证 Node 可跑）。
2. `Zombie` 拆分：`ZombieSim`（逻辑）+ `ZombieView`（渲染）。视图只依赖 sim 的**只读快照**。
3. `Game` 改为组装 `MatchSim` + 各视图。单人路径行为必须**逐帧等价**（用现有 1075 个单测 + E2E 兜底）。
4. 加一条 **`npm run sim:headless`**：在 Node 里跑一场无人对局 60 秒（`MatchSim` 直接驱动，不起服务器），断言不崩溃、僵尸数/波次推进正常、无 `document` 引用。

**验收**：
- `npm test` 全绿，覆盖率不低于现有门槛（`vitest.config.js` 的 98/89/97）。
- `npm run test:e2e` 10 个场景全绿。
- `npm run sim:headless` 通过，且 `ps` 观察单进程内存 < 100 MB。
- 单人模式体验无变化（同地图同帧率）。

> **M1 的风险点**：`Zombie.js` 1925 行里，AI 与动画混得很紧（`this.mixer.update`、`applyFlash` 散落在 `update` 里）。拆的时候**先机械复制**再**逐段剪**，每剪一段跑一次测试；不要一次性手写新文件。

### M2 · 服务器权威 + 二进制快照（3~4 天）
1. `server/room.js`：每场一个 `MatchSim`，全局 30 Hz ticker。
2. 协议 v2 二进制编解码（`src/sim/snapshot.js`），客户端 `ClientNet` 替换 `DuoSession`。
3. 删除 `DuoSession.sendHostState`、`Game.applyGuestInput`、`netGuest` 代理、`history` 命中回退（逻辑搬到服务器）。
4. **保留**配对/重连/`joinToken`/`MAX_MATCHES`/`ACCESS_CODE` 全部现有能力（`matchmaker.js` 只删 host 语义）。
5. 集成测试：`tests/integration/duo-server.test.js` 扩展为「起服务器 → 两个假客户端 → 断言快照连续、位置收敛」。

**验收**：两个浏览器（一个模拟手机 CPU 降速 6 倍）对局 5 分钟，**客人视角僵尸不跳变、p95 帧间隔 < 60 ms**；房主掉帧不再影响客人（用 Chrome Performance 面板的 CPU 6x throttle 验证）。

### M3 · 手感打磨（2~3 天）
1. 输入预测 + 回滚重放（§3.4）。
2. 实体插值 + 抖动自适应 `INTERP_DELAY`、外推上限冻结。
3. 命中**服务器裁决**：客户端上报 `(yaw, pitch, origin)`，服务器用历史快照 + 视线校验 + 冷却校验。
4. 现有 M2 的「guest 发 hit 请求、host 用 seq 回退」逻辑（`Game.applyGuestHit` / `applyGuestBell` / `applyGuestAoe`）**整体搬进 `MatchSim`**——这部分代码质量不错（有视线校验、头身球、冷却），几乎不用重写。
5. HUD 加延迟/丢包角标（`rtt` 已经在 `NetClient` 里有）。

**验收**：两人同图对射僵尸 10 分钟，**击杀归属、比分、爆头判定零分歧**；`rtt` 抖到 300 ms 时仍可玩。

### M4 · 健壮性与压测（2 天）
1. 断线重连 → `SNAP_FULL`；座位保 45 s；托管期该玩家由 `PlayerSim` 的 simple AI 站桩。
2. ~~`worker_threads` 分片~~ **砍掉**：2C8G 上单核容量是 8 场的 20 倍以上（§1.2），分片纯属多余复杂度。
3. 压测脚本 `npm run bench:rooms -- --rooms 8 --minutes 10`，输出 CPU / RSS / 出网带宽 / 月流量估算。**跑在 Lighthouse 本机上**，不跑在开发机。
4. 静态资源缓存策略（见 §5.1）：`dist/assets/*`（带 hash）与 `public/models/*.glb` 设 `Cache-Control: immutable`，把 27 MB 的首屏成本压成「每用户只付一次」。

**验收**：在本机 2C8G Lighthouse 上跑 8 场 / 16 人持续 10 分钟，**CPU < 5%、出网 < 2 Mbps、RSS < 300 MB**，游戏内无卡顿。

### ~~M5 · 可选传输升级~~（已定案不做）
WebSocket 二进制已足够（0.14 Mbps/场）。若将来真在高丢包下不达标，再单独立项，不占本次范围。

### 回滚策略
- M1~M3 期间**保留旧路径**：`DuoSession` 与 `ClientNet` 共存一个版本，用构建开关 `VITE_NET_V2` 切换；出问题一键回滚到房主权威。
- M4 完成后再删旧路径（`DuoSession.js`、`netGuest`、`applyGuest*`）。

## 6.5 语言选型裁决：JavaScript 部署 vs Rust 重写

> 结论先行：**先用现有 JavaScript 部署，不要用 Rust 重写。** 下面给数据，不给感觉。

### 6.5.1 服务器端的时间到底花在哪

把 14 只僵尸每 tick 的成本拆开实测（jsdom 环境，比裸 Node 慢，偏保守）：

| 组成 | 每 tick | 性质 |
| --- | --- | --- |
| **AI / 寻路 / 状态机逻辑** | **30.8 µs** | ← Rust 能优化的部分 |
| 快照字段打包（`serialize()`） | 33.7 µs | 数据本来就要写进缓冲，换语言收益很小 |
| `JSON.stringify` | 16.1 µs | **换二进制协议就整段消失**，与语言无关 |
| 合计 | 62 µs | |

关键判断：**换语言只能优化 30.8 µs 这一格，而且是有上限的。**

### 6.5.2 换 Rust 的收益是多少

| 口径 | 8 场每 tick | 占 30Hz 预算（33.3 ms） |
| --- | --- | --- |
| 现在（JS） | 0.50 ms | **1.5%** |
| 换 Rust（乐观假设快 2 倍） | 0.22 ms | **0.7%** |

省下 0.27 ms —— 而单 tick 预算是 33.3 ms。**两个数字都在统计噪声里。** 换句话说：就算 Rust 快 10 倍，你也不会多出一个房间的容量，因为瓶颈根本不在 CPU（见 §1.2，CPU 余量 10~40 倍，真正卡的是出网带宽和流量包）。

### 6.5.3 Rust 重写的真实代价

**不是「把 JS 翻译成 Rust」，而是把整个项目重做一遍。** 核心难点在于这套模拟代码深度耦合了游戏数据：

| 耦合数据 | 规模 | 说明 |
| --- | --- | --- |
| `ZOMBIES` 僵尸类型 | **30 种**，每种有 hp/speed/damage/scale/radius/armor/airborne/skill 配置 | 包含 slam/duck/dive/landing/ambush/phase/tea/clock 等一堆技能参数 |
| `WEAPONS` 武器 | 十余把，`pea/lob/hitscan` 三种弹道 + `aerial` 白名单 | |
| 波次公式 | `wavePlan` / `duoWavePlan` / `waveMaxAlive` / 配额 | 雪地骷髅、云园空投等特殊逻辑 |
| 地图 | **5 张**，每张要重新生成 `colliders` / `platforms` / `bounds` / 流场网格 / 拾取点位 | 现在是 Three.js 场景里顺带算出来的 |
| 模拟代码本体 | `Zombie.js` 1925 行 + `Player.js` 335 行 + `ZombieManager` / `WeaponSystem` / `ProjectileSystem` / `SunOrbs` / `WeaponPickups` / `CloudCombat` | |

更致命的是**双实现问题**：

> 单人模式必须跑在浏览器里。如果服务器用 Rust，而单人用 JS，那就是**要同时维护两份模拟逻辑**。任何一次数值调整（`config.js` 改一个 `hp`）、任何一次技能 bug 修复，都要在两边各改一遍并各自验证一致。这在 2 人小项目的规模下是**灾难性**的维护负担，而且必然会分叉——今天是改平衡，明天是修一个只在一端出现的 bug。

替代方案「单人模式也跑 WASM」可以避免双实现，但代价是：每次改 `config.js` 都要重新编译 Rust → 开发迭代速度从「热更新 1 秒」变成「编译几十秒到几分钟」，单人模式的包体也会因为 WASM 变大。为了一个 1.5% 的 CPU 占用，换来开发体验的大幅退化，得不偿失。

### 6.5.4 什么情况下才值得考虑 Rust

把触发条件写死，避免未来凭感觉决策：

| 触发条件 | 说明 |
| --- | --- |
| 单进程 CPU 持续 **> 60%** | 按 §1.2 的实测，这需要 **200+ 场**同时在线（400+ 玩家）。以本项目的定位，这基本不可能 |
| 或者目标变成 **竞技 PvP / 排位赛** | 需要服务端跑更重的判定（回放校验、反作弊、更密的 tick），届时才有意义 |
| 或者出现 **JS 性能实测瓶颈且已排除算法问题** | 先优化算法（对象池、避免 GC、复用缓冲），不要直接跳语言 |

**在上述条件发生前，架构上只需要做一件事：把模拟层和渲染层分干净**（这正是 M1 在做的事）。只要 `MatchSim` 是纯逻辑、不依赖 DOM/Three 场景对象，**将来真要换 Rust，也是换「执行器」而不是换「游戏逻辑」**——那时可以只把 AI 热点用 WASM 插件替换，甚至只用一个 Rust 写的 N-API 扩展，成本远低于现在推倒重来。

### 6.5.5 一句话

> **现在换 Rust = 用两周重写 + 永久双实现维护负担，换取不到 1% 的 CPU 节省和一个并不存在的瓶颈。**
> **不做。** 但 M1 的「模拟/渲染分层」会让这个决定在未来仍然可以低成本地重开。

## 7. 明确不做的事（避免范围蔓延）

- ❌ 无头 Chrome / Electron 当服务器（你的约束，也是技术上错误的选型）。
- ❌ **Rust / Go / C++ 重写服务器**（见 §6.5：收益 <1%，代价是双实现维护）。
- ❌ 服务端渲染 / 服务端 GLB 解析：服务器**只跑逻辑**，不加载任何 `.glb`。
- ❌ 确定性 lockstep / 帧同步（P2P 那套）：本项目是 PvE 合作，状态快照 + 预测/回放足够，lockstep 会把「随机数、浮点、输入同步」的复杂度放大数倍。
- ❌ 提高同屏僵尸数 / 加新玩法。本次是**纯底层重构**，玩法数值不变。
- ❌ 迁移到 TypeScript / 换状态管理库。现有 ES Module 约定继续。
- ❌ 把单人模式改成必须联网。

### 决策 6 带来的实施约束（一次性上线）

因为不拆中间版本，M1~M4 期间**线上跑的仍是旧链路**。因此：

- M1（抽模拟层）**必须保证单人模式行为完全等价**，否则重构期间的单人玩家会受影响。
- M2~M3 的新联网栈用构建开关 `VITE_NET_V2` 隔离，**默认关闭**，只在测试环境打开；直到 M4 验收通过才切默认为开。
- 切换时保留旧路径一个版本，出问题可一个开关回滚（见 §4 回滚策略）。

### 决策 5 带来的风险（已登记）

- **风险**：桌面模拟无法完全代表 iOS Safari 表现，可能出现「开发验收全绿、真机仍不理想」。
- **缓解**：上线后由你和朋友**实际打一局**做最终确认；若真机仍有问题，优先看插值延迟与快照频率这两个参数（`INTERP_DELAY`、tick 率），它们是无损可调的。
- **诚实边界**：本计划不会把模拟数据当作「问题已解决」的证据。
